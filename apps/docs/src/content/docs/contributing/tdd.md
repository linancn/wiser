## 项目开发方式

每项行为变更从一个可以说明业务风险的失败测试开始。测试不是事后覆盖率工作，而是协议、状态机和安全边界的可执行说明。

```text
选择真实行为 → 写失败测试 → 最小实现 → 全量验证 → 重构 → 小步提交
```

## 一次纵向循环

以“不能引用尚未释放的水源可用量修订”为例：

1. **红**：构造 T+06 Episode，调度方案引用 T+12 才释放的上游来水修订，期望稳定错误码。
2. **绿**：只实现 Observation 所有权和 `released_time` 检查。
3. **重构**：把相同规则提取为领域策略，并保持 HTTP、SDK、MCP 共用。
4. **提交**：测试与实现一起提交，消息描述行为结果。

不要先搭完整抽象层再寻找用例。一次循环应贯穿合约、数据库、API 和最小界面，让代码始终可以运行。

## 测试层级

| 层级       | 验证内容                               | 主要工具                    |
| ---------- | -------------------------------------- | --------------------------- |
| 单元       | 状态转换、评分函数、Zod schema         | Vitest                      |
| API 组件   | 状态码、幂等、错误 envelope            | Vitest + Fastify `inject()` |
| 数据库集成 | migration、约束、RLS、行锁、事件原子性 | 真实 Compose PostgreSQL     |
| 契约       | HTTP、SDK 与 MCP 使用同一 fixtures     | Vitest                      |
| 浏览器 E2E | 中文默认、英文切换、关键管理流程       | Playwright                  |
| AI smoke   | 供应商凭据和最小调用是否可用           | 显式 opt-in，不进默认 CI    |

关键事务和 RLS 不使用内存数据库替身。AI 测试相反：默认必须使用 fake adapter，保证可重复和零费用。

## 一个测试应回答什么

测试名使用业务语言，清楚表达：

- 给定哪个场景版本、参与者和虚拟时点；
- 执行了什么公开操作；
- 哪个可观察结果必须成立；
- 哪些隐藏数据绝不能出现在响应或事件中。

不要断言私有函数调用次数来代替业务结果。

## 完成定义

一项变更完成时必须满足：

- 新测试先失败过，当前通过；
- 相关负向、安全和幂等用例齐全；
- 中英文用户文案和协议文档同步；
- migration 可以从空数据库重放；
- `format:check`、lint、typecheck、test、build 全部通过；
- 没有把真实模型调用放入默认测试；
- 形成范围单一、可回退的 Git commit。
